# dsh-mcp-gateway v0.1.0

Release date: 2026-08-15

`v0.1.0` is the first release of `dsh-mcp-gateway`: an OAuth/MCP access adapter that gives ChatGPT Web a DSH Harness while keeping ChatGPT as the only primary reasoning/model agent.

## Core architecture

The supported path is:

```text
ChatGPT Web
    -> OAuth + MCP
    -> dsh-mcp-gateway
    -> DSH Harness / ToolRuntime / SkillRegistry
    -> local or optional downstream execution providers
```

DSH is the harness/runtime authority. The gateway does not require a second LLM provider and normal operation does not require `DEEPSEEK_API_KEY` or another model API key.

## Stable extension surface

The default ChatGPT-facing MCP surface is deliberately fixed to four meta-tools:

- `dsh_tool_catalog`
- `dsh_tool_call`
- `dsh_skill_catalog`
- `dsh_skill_load`

In default `meta-only` mode, `tools/list` stays fixed and the server does not advertise `tools.listChanged`. This makes DSH community extension availability independent of whether ChatGPT refreshes a previously approved first-class MCP tool snapshot.

An explicit `--tool-surface projected` mode remains available as a best-effort UX path for clients that support dynamic tool-list changes, but it is not required for correctness.

## DSH ecosystem validation

The release was validated against a pinned `@deepseek-ai/dsh@0.1.0-rc.6` runtime on Node 24.19.0.

Product-level acceptance demonstrated that community DSH tools installed after the ChatGPT App had already cached the four-tool MCP surface became discoverable and usable through `dsh_tool_catalog` / `dsh_tool_call` without reconnecting, rescanning, republishing, or changing the public MCP schema.

A separate SkillRegistry acceptance hot-added the independent `diagnosing-bugs` community Skill and verified that ChatGPT loaded it through `dsh_skill_catalog` / `dsh_skill_load` and materially changed its debugging workflow while the public MCP surface remained unchanged.

The long-running host used for final acceptance exposed 34 DSH-internal tools, including the community tools `calculator`, `json`, `regex`, `stat`, `time`, `encoding`, `csv`, `schema`, and `find_dsh_plugin`, plus the `diagnosing-bugs` Skill.

## OAuth and public deployment

The embedded OAuth server provides:

- dynamic client registration;
- PKCE public clients;
- persisted OAuth state;
- `offline_access` / refresh tokens;
- single-use refresh-token rotation;
- grant-family revocation;
- bounded registration and pending-authorization state;
- Host/Origin rebinding protection.

The production acceptance used a named Cloudflare Tunnel terminating at the loopback gateway. The raw DSH bridge remained private on loopback.

The public release smoke verified health/readiness, OAuth metadata, DCR, authorization/approval, token exchange, unauthenticated MCP rejection, MCP initialization, the exact four-tool surface, a 34-tool DSH catalog, and refresh-token replay rejection.

## Persistence and recovery

The v0.1 production layout uses systemd for:

- `dsh-web-host.service`;
- `dsh-mcp-gateway.service`;
- `dsh-cloudflared.service`.

Durable DSH state and OAuth state live under `/var/lib`. Nine community plugins were localized as self-contained artifacts under `/var/lib/dsh-harness/plugin-artifacts` so the installed profile does not depend on temporary acceptance directories.

Process-level cold-restart testing proved recovery of DSH tools, Skills, OAuth state, refresh-token rotation, the fixed four-tool contract, and the real ChatGPT Web client's automatic refresh flow without reconnecting or rescanning.

A production backup/restore drill also passed. The real production backup was restored into an isolated directory and separate loopback ports; the restored copy reproduced 34 DSH tools, `diagnosing-bugs`, the four-tool MCP surface, selected workspace data, and a working cloned ChatGPT OAuth refresh grant without modifying production services.

## Security boundary

The DSH bridge is loopback-internal. Public authentication and transport terminate at the gateway. The release includes an MIT `LICENSE` and `SECURITY.md` covering supported versions, private vulnerability reporting, deployment boundaries, and backup-secret handling.

## Known boundaries / deferred follow-ups

Two drills are intentionally not release blockers for v0.1:

- A full operating-system reboot drill is deferred to a normal maintenance window because the acceptance host also runs unrelated important projects. The systemd enablement and process-level cold-restart paths are already proven, but an actual host reboot has not yet been exercised.
- The optional projected `tools/list_changed` ChatGPT UX path remains a post-v0.1 client-behavior experiment. Meta-only correctness does not depend on it.

During strict ChatGPT acceptance, two absolute workspace-path reads were rejected by a platform pre-dispatch safety check while equivalent workspace-relative paths succeeded. Prefer workspace-relative paths in ChatGPT-facing workflows.

DSH itself is still a developer-preview dependency. Compatibility code is intentionally concentrated in the small bridge seam.
